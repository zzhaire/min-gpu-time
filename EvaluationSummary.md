# Evaluation Summary

This document summarizes the **trace-driven simulation evaluation** conducted for the GPU scheduling project and the artifacts generated under `results/`.
In all paper figures, our scheduler is referred to as **Eco-Pollux (Ours)** (internally corresponds to `pollux-patient` / `pollux_patient`).

## Experimental Setup

### Cluster

- **Topology**: 8 racks × 8 GPUs/rack = **64 GPUs**
- **GPU memory**: **80 GB** per GPU
- **Topology penalty model** (simulator):
  - **Single GPU**: penalty = 1.0
  - **Same rack multi-GPU**: penalty = `intra_rack_penalty` (default **1.4**)
  - **Cross rack multi-GPU**: penalty = `inter_rack_penalty` (default **2.1**)

### Workload

- Trace-driven synthetic workload generated by `utils/task_generator.py` with a fixed seed (default seed = 42) for reproducibility.

### Compared schedulers

- **Eco-Pollux (Ours)**: `PolluxPatientScheduler` (patient topology-aware placement + sharing-aware cost)
- Pollux: `PolluxScheduler`
- Min GPU Time: `MinGPUTimeScheduler`
- Rack Aware: `RackAwareScheduler`
- First Fit / Best Fit

## Metrics

- **Total GPU Time / Total GPU Hours**: primary cost metric (lower is better)
- **Average JCT**: mean job completion time
- **Average Wait Time**
- **Makespan**
- **Cost Per Task**: `Total GPU Time / #Tasks`
- **JCT CDF**: tail latency / fairness

## Experiments and Artifacts

### Experiment 1: Run-to-completion scalability (main experiment)

**Goal**: evaluate cost and latency scalability under high load using a run-to-completion setting.

- **Script**: `exp/run_scalability_completion.py`
- **Workload scheme**: nested workload (Scheme A)
  - generate a single max-scale workload once
  - for each N, use a prefix workload and rescale submission times
  - ensures different N share the same workload prefix for stronger comparability
- **N sequence**: `50, 100, 200, 300, ..., 1000`

**Data**:

- `results/scalability_completion.csv`

**Figures**:

- `results/scalability_completion_detailed.png`
- `results/scalability_completion_detailed.pdf`

**Key findings (high load, N=1000)**:

- **Cost reduction vs Pollux**: Eco-Pollux reduces **Total GPU Time by 12.3%** compared to Pollux.
- **Cost reduction vs Rack Aware**: Eco-Pollux reduces **Total GPU Time by 54.2%**.
- **Latency (vs Pollux)**:
  - **Avg JCT** improves by **11.3%**.
  - **Avg Wait** improves by **12.6%**.

### Experiment 5: Sensitivity to interference (robustness)

**Goal**: test robustness under different interference levels (sharing penalties).

- **Run script**: `exp/run_sensitivity.py`
- **Plot script**: `utils/plotting/plot_sensitivity.py`
- **Data**: `results/sensitivity_interference.csv`
- **Figure**: `results/sensitivity_plot.png`

**Quantitative definition of “interference”**:

Interference is modeled by a **GPU sharing efficiency map** `η(k)` (`sharing_penalty_map`), where `k` is the number of concurrent tasks running on the *same GPU*.
`η(k) ∈ (0, 1]` scales the effective progress rate when tasks share a GPU.

The experiment evaluates three regimes:

- **Low interference** (weak sharing impact):
  - `η = {1: 1.00, 2: 0.95, 3: 0.90, 4: 0.85, 5: 0.80}`
- **Medium interference** (default setting):
  - `η = {1: 1.00, 2: 0.85, 3: 0.65, 4: 0.40, 5: 0.20}`
- **High interference** (strong sharing impact):
  - `η = {1: 1.00, 2: 0.60, 3: 0.40, 4: 0.25, 5: 0.10}`

**How the simulator uses `η(k)`**:

For a running task, the simulator computes an effective progress rate per second (see `simulator.py`) as:

`effective_rate = (#allocated_gpus) * sharing_efficiency / placement_penalty`.

Here `sharing_efficiency` is derived from `η(k)` for each GPU the task occupies.
By default the simulator aggregates per-GPU efficiencies using **min aggregation** (`sharing_penalty_aggregation = "min"`), i.e., a multi-GPU job’s speed is bounded by the most contended GPU it uses.
Therefore, higher interference (smaller `η(k)`) directly reduces job progress rate and increases total busy time, which increases **Total GPU Time / GPU Hours**.

Observed Total GPU Time (GPU-seconds) for Eco-Pollux:

- Low interference: `485,785`
- Medium interference: `522,729`
- High interference: `642,334`

### Experiment 6: Pareto frontier (cost vs speed)

**Goal**: characterize the cost–speed trade-off and show Eco-Pollux forms the Pareto frontier.

- **Run script**: `exp/run_pareto.py`
- **Plot script**: `utils/plotting/plot_pareto.py`
- **Parameters swept**: 3 representative points (to straddle topology thresholds)
  - `Patience ∈ {1.2, 1.6, 2.4}`
- **Data**: `results/pareto_frontier.csv`
- **Figures**:
  - `results/pareto_frontier.png`
  - `results/pareto_frontier.pdf` (PDF readability improved: larger canvas, larger fonts, non-overlapping annotations, legend outside plot area)

**What is plotted (axes and how “cost” is computed)**:

Each point corresponds to one scheduler (or one parameterization of Eco-Pollux).

- **X-axis (Cost)**: total GPU time converted into a cloud cost proxy.
  - The raw metric is `Total GPU Time` in GPU-seconds (from the simulator).
  - In the plot we convert it to dollars with a fixed price assumption (see `utils/plotting/plot_pareto.py`):
    - `Cost($) = (Total GPU Time / 3600) * $3/GPU-hour`.
- **Y-axis (Speed)**: `Avg JCT` in seconds (lower is better).

**Why this is called a Pareto frontier**:

We say a point A **Pareto-dominates** point B if:

- A has **no higher cost** than B, and
- A has **no higher Avg JCT** than B,

and at least one of the two is strictly better.
The **Pareto frontier** is the set of non-dominated points that represent the best achievable cost–speed trade-offs.

**Quantitative results (from `results/pareto_frontier.csv`)**:

Baselines:

- Pollux: `Total GPU Time = 654,237`, `Avg JCT = 6,040.8` (Cost ≈ `$545.2`)
- Rack-aware: `1,278,069`, `8,156.4` (Cost ≈ `$1,065.1`)
- Min-gpu-time: `1,288,075`, `10,080.7` (Cost ≈ `$1,073.4`)
- First-fit: `1,342,273`, `9,237.4` (Cost ≈ `$1,118.6`)

Eco-Pollux (Ours), varying Patience:

- Patience=1.2: `Total GPU Time = 522,729`, `Avg JCT = 8,416.0` (Cost ≈ `$435.6`)
- Patience=1.6: `Total GPU Time = 635,600`, `Avg JCT = 5,876.4` (Cost ≈ `$529.7`)
- Patience=2.4: `Total GPU Time = 681,838`, `Avg JCT = 5,941.5` (Cost ≈ `$568.2`)

From these numbers:

- The three points are chosen to **straddle the topology thresholds** and represent three qualitatively different placement regimes.
- In the figure, we label Eco-Pollux points by **regime** rather than numeric Patience:
  - `Patience < δ_intra` (representative point: Patience=1.2)
  - `δ_intra ≤ Patience < δ_inter` (representative point: Patience=1.6)
  - `Patience ≥ δ_inter` (representative point: Patience=2.4)

**Meaning of Patience**:

- In code this is `patience_threshold` inside `PolluxPatientScheduler`.
- It is a topology-penalty tolerance threshold: only allocations satisfying `topo_penalty <= patience_threshold` are accepted; otherwise the scheduler waits unless starvation.

Interpretation:

- Smaller Patience means Eco-Pollux is more selective about placement topology (waits more aggressively for “good” placements), which typically reduces wasted GPU hours but can increase queueing and JCT.
- Larger Patience relaxes topology constraints (starts earlier with less ideal placements), which can reduce JCT at the expense of higher GPU-hours.
- The topology penalty has two key values for multi-GPU placements in our cluster model:
  - `δ_intra = intra_rack_penalty = 1.4` (multi-GPU within the same rack)
  - `δ_inter = inter_rack_penalty = 2.1` (multi-GPU across racks)
- This makes `patience_threshold` a **topology gate**:
  - If `Patience < 1.4`, Eco-Pollux effectively rejects even same-rack multi-GPU placements for the “valid candidates” set and waits more.
  - If `1.4 <= Patience < 2.1`, Eco-Pollux accepts same-rack placements but still rejects cross-rack placements.
  - If `Patience >= 2.1`, Eco-Pollux also accepts cross-rack placements.
- As a result, the Pareto curve can appear **step-like**: multiple Patience values in the same interval (e.g., 1.0–1.3) may yield identical outcomes because they admit the same topology classes.
- In the figure, we label Eco-Pollux points by **regime** rather than numeric Patience:
  - `Patience < δ_intra`
  - `δ_intra ≤ Patience < δ_inter`
  - `Patience ≥ δ_inter`

```bash

python -u exp/run_scalability_completion.py

# Experiment 1 plots
python utils/plotting/plot_scalability_completion_detailed.py \
  --csv results/scalability_completion.csv \
  --out-png results/scalability_completion_detailed.png \
  --out-pdf results/scalability_completion_detailed.pdf

# Experiment 2: main summary figures (derived from Experiment 1 @ N=1000)

```
